## 2. Onchain Execution & Calldata Structure

Inspection of [`ModularSmartAccount.sol`](file:///Users/kishorevarma/Desktop/drop%20chain/contracts/src/core/ModularSmartAccount.sol) and [`DropValidator.sol`](file:///Users/kishorevarma/Desktop/drop%20chain/contracts/src/DropValidator.sol):

1. **Outer Function Selector:**
   `ModularSmartAccount.execute(bytes32 mode, bytes calldata executionCalldata)`
   - Selector: `0xe9ae5c53` (`IERC7579Execution.execute.selector`).
   - `mode`: Must be single call with `bytes1(mode[0]) == 0x00` (e.g., `bytes32(0)`). Delegatecall (`0xff`) and batch modes are strictly rejected.

2. **Execution Calldata Layout (`executionCalldata`):**
   `abi.encodePacked(address target, uint256 value, bytes innerCallData)`
   - `target` (bytes 0..20): Must match `policy.token`.
   - `value` (bytes 20..52): Must be strictly `0` (rejection of native ETH transfers).
   - `innerCallData` (bytes 52..120): Exactly 68 bytes for standard ERC-20 transfers:
     - `innerSelector` (bytes 0..4): Must be `0xa9059cbb` (`IERC20.transfer(address,uint256)`).
     - `recipient` (bytes 4..36): 32-byte word containing the recipient address.
     - `amount` (bytes 36..68): 32-byte word containing the token transfer amount.

## 3. Session Policy Representation

Stored in `DropValidator.sol` under `sessionPolicies[account][sessionKey]`:

```solidity
struct SessionPolicy {
    address sessionKey;     // Authorized agent address
    address token;          // Whitelisted ERC-20 token address
    address recipient;      // Whitelisted recipient address
    uint256 maxAmount;      // Maximum allowed per-transaction amount (e.g. 400 * 10^6)
    uint256 dailyBudget;    // Maximum cumulative daily spending limit
    uint48 validAfter;      // Start timestamp (inclusive)
    uint48 validUntil;      // Expiration timestamp (inclusive)
    bool enabled;           // Policy activation flag
}
```

## 4. ERC-4337 `PackedUserOperation` Construction

In the testing harness and live execution:
- `sender`: The `ModularSmartAccount` address.
- `callData`: The encoded call to `ModularSmartAccount.execute(mode, executionCalldata)`.
- `signature`: Raw ECDSA 65-byte signature generated by signing `opHash = mockEntryPoint.getUserOpHash(userOp)` directly with the agent's private key (`agentAccount.sign({ hash: opHash })`).
- `accountGasLimits`, `gasFees`, `paymasterAndData`, `nonce`, `initCode`: Standard ERC-4337 v0.7 fields.

## 5. Architectural Implications for Phase 2

1. **Intent Schema (`packages/intent-schema`):**
   - Must strictly represent `ERC20_TRANSFER` intent with exact types (decimal string amounts, valid checksum/hex addresses, explicit chain ID, account, mandate ID).
   - Must reject floating-point numbers, negative values, and arbitrary parameters.
   - Must provide deterministic normalization and stable cryptographic hashing.

2. **Canonical Builder (`packages/canonical-builder`):**
   - Must translate validated intent into:
     - Low-level canonical transaction parameters: `{ target, value: 0n, callData }` with selector `0xa9059cbb`.
     - Standard ERC-7579 execution calldata: `{ mode: bytes32(0), executionCalldata: concat([target, pad(0, 32), callData]) }`.
   - Must derive the deterministic **Expected Effect**:
     `{ type: "ERC20_TRANSFER", token, from: account, to: recipient, amount }`.
   - Must guarantee that no parameter is mutated or injected between intent, transaction, and expected effect.
